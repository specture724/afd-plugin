# 四节点 GPU prefill 性能比较

测试日期为 2026 年 11 月 25 日，AFD Plugin 提交为 `5989c683e11fde0e73081e77ed56c09e7d7f720e`。[汇总 CSV](summary.csv) · [性能对比图](prefill-comparison.png)

## 正式结果（HTTP keep-alive 5 秒）

**长请求领先 50 ms 时，Async 的短请求首 token 延迟最低。** 在 24A/8F，短请求 p95 TTFT 从单独运行时的 85 ms 增至 101 ms。相同两种场景下，DeepEP M2N 从 62 增至 513 ms，P2P NCCL 从 100 增至 817 ms。原生 wide EP 配对时为 376 ms，16A/16F 的 Async 为 137 ms。

七种配置、每种三个种子、每个种子 32 对，共 672 对。短请求全部在长请求首 token 到达前发出，并在长请求结束前收到完整响应。同步方案下短请求同样先返回，但长请求增加了它们的首 token 等待时间。Async 缩短了这段额外等待。

**64 RPS 混合输入吞吐以原生 wide EP 最高，达 108,508 tok/s。** 在 24A/8F，DeepEP M2N 为 98,867 tok/s，P2P NCCL 为 76,047 tok/s，Async 为 60,518 tok/s。

原生 wide EP 在 H20-3e 上没有每 rank 两个专家、N=1408 的 fused-MoE 调优配置表，vLLM 使用了默认内核配置。

独立的 30 秒 HTTP keep-alive 对照中，64 RPS 输入吞吐相对正式结果的变化为 DeepEP M2N 24A/8F +0.29%、原生 wide EP -0.13%，两者绝对差均小于 1%。主表全部采用 5 秒设置。

七个配置中 7 个通过全部 3 个种子的测量与版本校验。每个配置使用 4 节点、32 张 H20。模型为 DeepSeek-V2-Lite-Chat，BF16、TP1、decode FULL graph、DBO 关闭、prefix cache 关闭。每请求生成 1 token。

本表的 HTTP keep-alive 统一为 5 秒。每个配置选择该设置下第一个完整通过的作业。旧节点清单缺少此字段时，使用固定版 vLLM 的默认值 5 秒。两种设置共用相同的请求计划、到达时序和 DP 映射。

原生 wide EP 的 all-to-all 后端为 `allgather_reducescatter`。Poisson 实验中约 80% 为 256-token 短请求、20% 为 16,384-token 长请求。短请求轮询一半 DP rank，长请求轮询另一半，三个种子间轮换两组的 rank。这样会产生可复现的 prefill 不均衡，用于观察短请求是否因其他 rank 的长请求而等待。

值为三个种子的中位数，括号内为最小值和最大值。TTFT 从计划到达时刻算起，包含客户端派发延迟。Poisson 的吞吐率包含到达窗口和最后一个请求排空的时间。


七个计量配置使用同一组四台 H20 节点。核对 Slurm 分配、启动命令对应的节点和各节点的 GPU 快照后才能计入结果。

每个节点保存启动前、服务就绪和测量结束时的 GPU 进程快照。启动前要求 8 张卡没有计算进程，后两次要求 8 张卡全部由当前 Slurm 作业占用，逐进程核对 cgroup 作业号。

按 Slurm 作业编号选最早完整且通过校验的尝试。每次启动都需要逐 rank warmup、4 个节点上的全部 GPU 进程证据、12 份零错误结果，并与事先冻结的工作负载及 rank 映射 SHA 和逐请求记录一致。
